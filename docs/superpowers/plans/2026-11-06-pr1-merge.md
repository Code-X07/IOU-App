# PR #1 merge: Compose UI into main (single part)

> **For agentic workers:** use superpowers:subagent-driven-development or superpowers:executing-plans, one task at a time. This plan is a single part, deliberately short: each task names the files, the change and how to verify it. It has no code blocks. Read the finding in the review before starting a task.

**Goal:** land the friend's Compose UI ([Code-X07/IOU-App#1](https://github.com/Code-X07/IOU-App/pull/1), `feat/compose-ui`) on current `main`, with every finding F1–F14 of the [integration review](../../reviews/2026-11-06-pr1-integration-review.md) fixed, so M2 can start.

**Approach:**
- Work on a new branch, `integrate/compose-ui`, cut from `origin/main`.
- Merge `origin/feat/compose-ui` into it as a real merge commit, so the friend's four commits stay in history.
- Fix the findings task by task, all in this one part.
- Open a new PR that supersedes #1 and ask the friend to review it.
- The friend's remote branch is never modified.

**Who:** we implement everything, including screens and ViewModels (owner decision, 2026-11-06). Keep the friend's structure and style, and change only what a finding needs. This is integration work, not a UI rewrite.

## Global constraints

- **No M2 work.** XLSX export and group-row CSV import stay out (F12 removes the XLSX option; it doesn't implement it).
- No platform or dependency upgrades, even where lint warnings suggest them.
- Never switch the real flavor back to `FakeApis` to make UI assumptions hold.
- No lint suppressions or baselines to get a green build, and no blanket `else` in `LedgerError.userMessage`.
- Core owns lock policy and `FLAG_SECURE`, through `AppSecurity`, `TimedLockGate` and `SettingsApi.observeLockRequired()`. The UI covers content and calls `markUnlocked()` only after a successful system authentication.
- Use only synthetic data on devices. Use a disposable AVD, never the original emulator-5554 image (see the device-safety rules in the local project notes).
- Toolchain:
  - Use `JAVA_HOME` = MS JDK 21 and `--no-daemon`.
  - Run assemble, then lint, as separate commands; combining them races on Hilt-generated sources.
  - `minSdk` is 30, so avoid newer APIs; for example, use `atZone().toLocalDate()`, not `LocalDate.ofInstant`.
- Every behavioural fix gets a regression test. The review's seven probes are in the review's local diagnostic clone (`.../ui/viewmodel/Integration*ReviewTest.kt`). Port each one into the task that fixes it.
- Keep the spec, `docs/ui-contributor-guide.md` and `docs/manual-test-checklist.md` in step with the code in the same task that changes behaviour.
- One commit per task, at least. Don't add attribution. Push the branch and open the PR only when the owner says so.

**Workflow note:** the project's agent rules default to Haiku implementers, but this plan has no verbatim code to copy. Run the implementers on Sonnet (the orchestrator's escalation judgement) with Sonnet reviewers. Per-task reviews as usual; the orchestrator does one whole-branch review at the end of the part (Task 7).

Paths in the tasks are relative to `android/app/src/main/kotlin/io/github/codex07/iou/` unless they start with `android/` or `docs/`.

## Task 3: Lock and secure-window ownership (F6, F7)

1. **F6.** In `ui/viewmodel/SecurityViewModel.kt`:
   - Remove `localLocked`, and remove `background()` setting it.
   - `locked` becomes `enabled && backendLocked`, where `backendLocked` comes from `observeLockRequired()`.
   - Keep the privacy cover while the app isn't in the foreground (`!foreground`). That is a cover, not a timeout.
   - Keep successful authentication as the only path to `markUnlocked()`.
   - After a ledger replacement, rely on the backend lock state; don't force a lock.
2. **`FLAG_SECURE` ownership.** `AppSecurity` already applies it to every activity from settings. Remove the competing secure-window code:
   - the `FLAG_SECURE` add/clear calls in `MainActivity` (`onCreate` and `onPause`);
   - the `protectScreen` callback and `secureWindow` in `IouRoot` and `SecurityViewModel`.

   If the cover isn't drawn early enough for Recents (checked on the device), decide with the owner; don't add a second policy.
3. **F7.** Track generation health and settings health separately in `SecurityViewModel`. Content is uncovered only when both streams are healthy. A failed generation stream keeps the content covered and shows "Reopen the app"; a later settings emission doesn't clear it.
4. Tests:
   - Port both security probes.
   - Rewrite `SettingsSecurityTest` "foreground fallback is conservative…" to check that the UI follows `observeLockRequired` for each timeout.
   - Keep the replacement, cancellation and prompt-callback tests passing.
5. Device check:

   - With screen protection on and off, check screenshots and Recents.
6. Update the `docs/manual-test-checklist.md` app-lock section to use the real UI instead of the placeholder activity.

**Done when:** a short return within the timeout stays unlocked, a generation failure stays covered, and `FLAG_SECURE` has one owner.

## Task 4: Data lifecycles (F9, F10, F11)

1. **F9.** In `ui/viewmodel/DataManagementViewModel.kt`:

   - Calling it twice is harmless (the API ignores ended previews).

   - Reject duplicate actions during that window.

   - Call `dismissRestoreInterrupted()` only when the user acknowledges it.
4. **SAF grants** (review, "smaller actions"). In `DataManagementScreen.kt:43–51`, stop calling `takePersistableUriPermission`: every operation uses its URI immediately, so the temporary grant is enough. That also removes the "persist failed means access failed" path. Read and write errors still arrive as `FileAccessFailed`.

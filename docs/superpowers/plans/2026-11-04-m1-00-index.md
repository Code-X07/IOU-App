# Milestone 1 Implementation Plan: Index

> **For agentic workers:** this file is the map. Each part below is its own plan with its own header; execute them in the order given with superpowers:subagent-driven-development (recommended) or superpowers:executing-plans. Read this index first: its **Locked decisions** and **Type inventory** apply to every part, together with the M0 index (`2026-11-02-m0-00-index.md`), whose locked decisions still hold unless this file overrides them.

**Goal:** Milestone 1 of the MVP spec (`docs/superpowers/specs/2026-11-02-iou-mvp-design.md` §12): the `real` flavor is a working personal ledger on Room. It has history and revert, merge and unmerge, FX with a rate cache, encrypted JSON backup and restore with crash safety, CSV export, own-export import with undo, app lock and screen protection.

**How these plans were written:** every part's code was built and tested in a scratch workbench before its plan was written. The code blocks are that workbench's files, copied by a script (`.superpowers/tools/expand-plan.js`, untracked), so each task's code compiles and its tests pass as given. Each task was checked out and tested on its own. If a step's code and its prose disagree, the code is right; report the prose.

## M1 acceptance criteria (spec §12, verbatim)

1. A 50.00 EUR loan from me to X shows "X owes you 50.00 EUR". A 20.00 EUR repayment from X to me changes it to 30.00 EUR, regardless of account label.
2. Balances in two currencies are shown separately; the combined home-currency total is labelled approximate.
3. An untagged transfer between two people who are not me, and an ad-hoc expense with three people, are rejected with `NeedsGroup`.
4. Editing a transfer from 40.00 to 45.00 adds an `UPDATED` revision whose diff shows "40.00 → 45.00 EUR"; reverting to v1 brings back 40.00 and adds a further revision.
5. Deleting a transfer removes its effect immediately; restoring brings it back; both appear in history.
6. Two duplicates "Alex" (owes me 10.00) and "Alex S." (owes me 5.00) merge into one person who owes me 15.00. Their old entries still show their original revisions, and unmerging restores 10.00 / 5.00. If "Alex" was first merged into "Alex S." and "Alex S." is then merged into "A. Smith", unmerging "Alex S." takes "Alex" along and restores the balances from before the second merge.
7. JSON backup → wipe → restore yields identical balances, IDs, versions, revisions and the same me identity; the device ID is unchanged by the restore.
8. Restoring with a wrong passphrase writes nothing and shows "Wrong passphrase or damaged file". A failure injected before the commit point leaves the previous database and ledger settings intact. "Undo last restore" after a successful restore brings back the previous state.
9. A text field `=HYPERLINK("http://evil","x")` exports as text in CSV, and re-importing the export restores exactly `=HYPERLINK("http://evil","x")`; a note `'quoted` also round-trips unchanged.
10. Importing an export in which a transfer was edited differently from the local copy (even with a higher source version) shows a conflict with a field diff. Nothing is overwritten unless "take incoming" is chosen, and the resulting revision records the source file and version. A transfer deleted in the export but active locally shows as a conflict "active → deleted"; taking incoming deletes it (and the reverse restores it).
11. Importing an export from a fresh second install (different me identity): after confirmation, its transfers with X arrive as transfers between the local me and X, pass all §3.4 rules, and their origin revisions record the identity mapping. Declining rejects the import with `ForeignLedger` and writes nothing.
12. Killing the process at each step of a restore and of an undo (test hook) leaves, after restart, either the complete old database or the complete new one, never a mix. A kill before the commit point keeps the old database and is reported once; a kill after it keeps the new one and reports nothing.
13. With no manual backup for 30 days, `BackupApi` reports the reminder; making a backup clears it.
14. The M0 contract tests for setup, people, the non-group ledger, FX, backup, import/export and settings pass against the real implementation. Contract tests that need groups are tagged `groups` and join the real run in M2; until then the real flavor's `GroupsApi` emits no groups and rejects writes.
15. After a restore commits, `observeLedgerGeneration()` emits a new value. Saving an edit draft loaded before the restore returns `LedgerReplaced` and writes nothing, even when the restored entry has the same version number; saving a settle-up or other create draft prepared before the restore, and committing an import preview parsed before it, do the same. After "Undo last restore", the generation changes again, and a token from before the restore is still rejected with `LedgerReplaced`, although the entry is back at that version.
16. An import file containing two deleted people whose `mergedIntoId`s point at each other is rejected with those rows invalid (`CorruptData`).
17. Changing a converted transfer's paid currency while trying to keep its old snapshot is rejected (`FxSnapshotMismatch`); the user must take a new rate.
18. X owes me 100 SEK. A 9.00 EUR repayment from X, recorded from the person settle-up draft with `settlesCurrency` SEK and a rate giving a 100 SEK effect, brings the SEK balance to 0 and leaves the EUR balance unchanged. Editing only its note keeps the snapshot and the SEK effect; clearing `settlesCurrency` drops the snapshot and turns it into a 9.00 EUR effect.
19. A 1 000 SEK transfer with a bank-actual charge of 87.65 EUR (snapshot records 1 000 SEK and 87.65 EUR) keeps that snapshot and effect when only its note or date is edited. Changing the paid amount to 2 000 SEK while keeping the snapshot is rejected with `FxSnapshotMismatch`; saving with a new charged amount or a looked-up rate succeeds.
20. An import file with a 1 000 SEK transfer, a new `USER_ENTERED` snapshot at 0.09 EUR/SEK and an effect of €100 shows that transfer as invalid (`FxSnapshotMismatch`, rule 17), and so does an unconverted transfer whose effect amount differs from its paid amount.
21. Adding a payment handle to a person after an import preview was built makes the commit return `ImportPreviewStale` with nothing written. The refreshed preview keeps the earlier choices and shows the new handle under the person's cascade.

**Changed by this plan (locked decisions 6 and 7):** AC 14's restriction on groups no longer applies. The real flavor has working groups in M1, and the `groups` contract tests run against it. Import undo (spec §5.4, an M2 item) is built in M1 for M1's import types.

## Locked decisions (apply to every part)

1. **Packages.** New in M1: `store` (Android-free; the shared store and the `Store*Api` classes), `data` (Room, files, the real backend), `fx` (Android-free; Frankfurter, rate table, lookup chain), `io` (Android-free; CSV export and import), `security`. Dependency direction: `money` ← `ledger.model` ← `api` ← `ledger.*` ← `store` ← `fx`, `io` ← `data` ← flavor `di`, and `store` ← `fake`. `store` imports nothing from `fake`, `fx`, `io` or `data`; `fx` and `io` import nothing from `fake` or `data`. `data` may use the `fake` simulations only until the part that replaces them.
2. **One store for both flavors** (ADR-0010). The real flavor keeps the whole ledger in memory and persists each validated write through `RoomJournal` before publishing it. Nothing else writes the ledger tables (`DataAccessTest`).
3. **Room on the driver API.** Room 2.8.1 uses `AndroidSQLiteDriver` (`sqlite-framework`) on the device and `BundledSQLiteDriver` (`sqlite-bundled-jvm`, test only) in JVM tests. DAO functions are `suspend`; transactions are `useWriterConnection { immediateTransaction { } }`. Journal mode is WAL: a closed database is a single file again. Rows are replaced with `@Insert(onConflict = REPLACE)`, never `@Upsert` (Part 2).
4. **Tests stay on the plain JVM with JUnit 5.** Room runs with `TestDatabases` (a `ContextWrapper` that only resolves database paths) and `unitTests.isReturnDefaultValues = true`. There is no Robolectric and there are no instrumentation tests. On-device checks run on the emulator AVD `Medium_Phone_API_37.0`.
5. **Persisted values** are text and integers: instants as ISO-8601 (`Instant.toString`, nanoseconds kept), dates as ISO `yyyy-MM-dd`, money as minor units plus an ISO code, rates as decimal strings, enums by name. The rows are also the JSON shape of revision snapshots and backups.
6. **Groups are live in the real flavor from Part 3.** All contract suites, `groups` tests included, run against both backends. CSV import of group rows arrives in M2; until then such rows are invalid rows in the preview.
7. **Import undo is built in M1** (Part 7), for people, payment handles, transfers, ad-hoc expenses and FX snapshots.
8. **Device-local settings** live in `noBackupFilesDir/device-settings.json` (`FileDeviceSettings`), not DataStore: DataStore can't replace its file on Windows, which broke local JVM tests. The device ID is `noBackupFilesDir/device-id`.
9. **All ledger files** live in the app's database directory: `iou-<uuid>.db` files, `db-state.json`, `db-state.json.tmp`, `restore-marker.json`.
10. **Versions** stay pinned as in M0, plus: Room 2.8.1, androidx.sqlite 2.6.1, kotlinx.serialization 1.9.0 (plugin = Kotlin 2.2.20). Parts 4–8 add Ktor 3.2.3 (`ktor-client-core`, `-okhttp`, `-mock` for tests), Apache Commons CSV 1.14.1, BouncyCastle `bcprov-jdk18on` 1.81, WorkManager 2.10.3 (`work-runtime`, real flavor only) and `lifecycle-process` 2.9.2. All of these resolved and compiled with the toolchain on 2026-11-04. `androidx.hilt:hilt-work` is not used: the refresh worker reaches the backend through a Hilt entry point (Part 4).
11. **M0 plan files are frozen history.** M1's changes to M0 code are documented here only and not mirrored into `2026-11-02-m0-*.md`.
12. **Git** as in M0: commit after every task, push straight to `main` after the owner approves, plain messages, no attribution, LF endings. Only `android/`, `docs/`, `.github/` and `README.md` are tracked.
13. **API changes** (spec §6.4) touch `api`, the fake and the real backend together. The friend is told about each one: Part 5 adds the interrupted-restore notice to `BackupApi`, the errors `FileAccessFailed` and `RestoreFailed`, and the passphrase rule; Part 6 rejects XLSX until M2; Part 7's previews don't survive an app restart (`NotFound("preview")`).
